# AGENTS.md

Notes for AI agents working in this repo.

## What dezi is

An arbitrary-precision decimal library aiming at decimal.js parity, but opt-in: a tiny core (`src/decimal.ts`) plus small extension modules a consumer imports individually or via presets (`src/preset/*`). The README documents what exists; `ROADMAP.md` lists only what is still missing.

## Hard rules from the maintainer

- The published `package.json` (metadata, `exports`) is generated by `build.ts` into `dist/`; the root `package.json` is private and carries no `exports`. Publish from `dist/`.
- **No hacky solutions.** Never post-process or rewrite `declare module` expressions, never add code-heavy workarounds. Type-level extension via interfaces must keep working as designed.
- No new dependencies, no new folder kinds without maintainer approval.

## Invariants (deliberate deviations from decimal.js)

- **No NaN, no ±Infinity, no signed zero.** Parse is strict; operations that would produce non-finite results throw `RangeError` instead of saturating (division by zero, `sqrt` of a negative, `ln`/`log` of a non-positive, inverse functions outside their domain).
- Zero is always `[0n, 0]`.
- Results beyond `±Decimal.exponentLimit` throw `RangeError` in both directions — underflow does not flush to zero.

## Architecture

- `src/decimal.ts` — the core: `interface Decimal` (instance merge target), `interface DecimalConstructor`, `DecimalLike`/`RawDecimal` types, and `const Decimal` backed by an internal class (one documented boundary cast).
- Extensions live in kind folders, categorized by what they return/touch:
  - `src/ops/` — return new Decimal values (plus, divide, sqrt, max, floor, …)
  - `src/check/` — questions about a value: booleans, comparisons, counts, guards
  - `src/format/` — output representations (toString, toFixed, toNumber, …)
  - `src/config/` — global settings and value-less factories (precision, rounding, set…)
- Each extension has exactly **one** `declare module "dezi"` block declaring both interfaces and any exported types (e.g. `RoundingMode`). Runtime members attach via `extend()`/`extendStatic()` from `src/utils/extend.ts`; aliases must also be declared inside the block.
- Augmentations must also typecheck for a consumer who imports just that one extension (next to `"dezi"`), where no other extension's declarations are loaded — `pnpm run check-consumer` verifies every subpath of the build this way:
  - A type declared by another extension (`RoundingMode`, `PrecisionOptions`) needs a direct side-effect import of the declaring config extension under `// required extensions`; the emitted `.d.ts` keeps only direct imports.
  - A block that augments only `DecimalConstructor` refers to the instance type as `import("dezi").Decimal`: inside the block, a bare `Decimal` resolves only where some loaded extension augments `interface Decimal`.
- The `"dezi"` specifier is type-level only in-repo: use it for `declare module "dezi"` and `import type` (tsconfig paths maps it to `src/index.ts`; consumers resolve it via package self-reference). Runtime imports in `src/` and `test/` are always relative (`../decimal.ts`, `../src/preset/full.ts`) — vitest does not resolve `"dezi"`.
- Canonical values: `parse()` (and therefore `new Decimal(...)`) normalizes every input and range-checks the normalized exponent against `Decimal.exponentLimit` (±999 999). Ops build results as raw tuples and return `new Decimal(raw)` — no op needs its own normalize or range check. Only ops that would otherwise compute a gigantic intermediate (`pow`, `exp`) pre-check and throw `exponentRangeError()` early. Inside ops read the receiver via `this.raw`/`this.coefficient`, never `parse(this)`.
- Config statics are owned by extensions, not the core constructor (`precision` lives in `src/config/precision.ts`, notation thresholds in `src/format/to-string.ts`); consumers read them through side-effect imports of the owning extension.
- Static methods are the exception: only receiver-less operations (`max`, `min`, `sum`, `hypot`, `arctan2`, `sign`, `isDecimal`) and the two-sided `compare` allowlist. No `Decimal.add(x, y)`-style mirrors of instance ops.
- Arithmetic family is exact (bigints); divide/transcendental ops are precision-based: they round to `Decimal.precision` significant digits using `Decimal.rounding` (a string-union `RoundingMode`, default `"half-up"`). Every such op takes a trailing `options?: PrecisionOptions` (`{ precision?, rounding? }`, declared in `config/precision.ts`) and resolves it via `currentPrecision(options?.precision)`/`currentRounding(options?.rounding)`, which fall back to the statics and validate; explicit `mode` parameters go through `currentRounding(mode)` too.
- Precision-based ops round **once**: never chain public precision-rounded ops (`a.ln().divide(b.ln())`) — call the `*ToPrecision` helpers with guard digits and round the final value with `roundToPrecision`, or `roundApproximation` when an exact result must survive directed modes. Verify new math against decimal.js on randomized inputs across precisions and all nine modes.
- Naming: verb primaries without filler words (`divide`, not `dividedBy`; `lessThanOrEqual`, not `lessThanOrEqualTo`), short aliases (`div`, `sub`, `gt`).
- Public API signatures use meaningful parameter names, never generic single letters (`sign(value)`, not `sign(x)`; explicit pairs like `compare(a, b)` are fine). Variadic value lists use `...values`.
- JSDoc describes dezi's behavior in its own terms; never mention decimal.js in JSDoc. Internal file comments may reference decimal.js for design context.
- Simple shared helpers live in `src/utils/` and are imported, never redeclared per extension file. Check these before writing a local copy:
  - `utils/common.ts` — `normalize`, `pow10` (table-backed, use it instead of `10n ** …`), `abs`, `digitsOf` (instead of inline `.toString().length`), `addRaw` (exact aligned addition), `LOG2_10`/`LOG10_2` float seeds
  - `utils/rounding.ts` — `roundingIncrement` (the nine modes against your own half/discard probes), `roundQuotient` (rounded integer division), `roundToScale` (quantize to `10^k`), `roundToPrecision` (to n significant digits), `roundApproximation` (final rounding of a guard-digit approximation, snapping exact results)
  - `utils/division.ts` — `truncDivide`, `divideToPrecision`; `utils/integer-roots.ts` — `isqrt`/`icbrt`, `rootToPrecision`; `utils/logarithm.ts` — `lnToPrecision`; `utils/exponential.ts` — `expToPrecision`
  - `utils/config.ts` — `currentPrecision()`, `currentRounding()`; `utils/parse.ts` — `parse` for every `DecimalLike` argument, `exponentRangeError`; `utils/string.ts` — `exponentialString`, `plainString`

## Reference: decimal.js source

<https://raw.githubusercontent.com/MikeMcl/decimal.js/refs/heads/master/decimal.js>

decimal.js is dezi's parity target and doubles as a reference for how an implementation of a math operation can look (rounding pipelines, argument reduction, series summation, exponentiation by squaring). Read it as **inspiration, not source**:

- The code is dated and does not use `bigint`: it stores digits in arrays and rounds in every operation — none of that carries over.
- Re-express its algorithms on dezi's primitives: normalized `[coefficient, exponent]` bigint pairs, the rounding helpers in `src/utils/rounding.ts`, and the precision/guard patterns of `src/utils/division.ts`, `src/utils/integer-roots.ts` and `src/ops/log.ts`.
- Keep dezi's invariants (throw instead of NaN/±Infinity, no signed zero) and dezi's naming (as listed in `ROADMAP.md` for planned extensions), never decimal.js's.

## Workflow for a new extension

1. One file in the right folder, one test mirrored in `test/<folder>/<name>.test.ts` (vitest, imports the extension for side effects via relative path). vitest hides `console` output of passing tests; use assertions, not logs.
2. Augmentation block, `extend()`/`extendStatic()` registration, side-effect imports of dependencies (last import lines, after a blank line, under the comment `// required extensions`), JSDoc on public members.
3. Remove the item from `ROADMAP.md` and add it to the README (preset/extension tables, "Not yet available" line); add the extension to presets only when asked (`src/preset/full.ts` is the exception: everything shipped belongs there, and `test/presets.test.ts` covers it).
4. When asked to implement several extensions, use one subagent per extension (their file sets are disjoint).
5. Validate with `./node_modules/.bin/tsc --noEmit`, `./node_modules/.bin/vitest run`, `./node_modules/.bin/biome check .`, `node build.ts`, and `pnpm run check-consumer` (after the build). For performance-relevant changes also run `pnpm run bench [filter]` (`scripts/bench.ts`: dezi vs decimal.js in plain Node, asserts equal results first; add a case for new hot paths) and `node scripts/bundle-size.ts` (per-preset min+gzip size). Dependencies: `pnpm i`.

- Style: tabs, double quotes, biome-clean, `import type` for type-only imports, no `any`. Use `type` for type declarations; `interface` only where declaration merging requires it: the `Decimal`/`DecimalConstructor` targets in `src/decimal.ts` and inside `declare module "dezi"` blocks.
